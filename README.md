# openjiuwen_challenge_2026

## GradientAI Harness: Budget-Aware Agentic AI

**Кейс:** оценка токенов для задач ИИ-агентов.

Предскажите, сколько токенов потребуется агенту до и во время выполнения задачи.

Высокопроизводительный харнесс кодового агента, разработанный командой **GradientAI** для студенческого соревнования НГУ по искусственному интеллекту (2026).

Система оптимизирована для максимизации количества успешно решённых задач при строгом ограничении в **100 000 токенов**. Основной принцип архитектуры — **Deterministic-First (детерминизм прежде всего)**: агент по возможности решает задачи локально, обращаясь к языковой модели только тогда, когда это действительно необходимо.

---

## 🏗 Архитектура и использование openJiuwen

Харнесс разработан с соблюдением требования использования экосистемы `openjiuwen`: пакет импортируется при запуске и присутствует в `process_tree`, что обеспечивает соответствие требованиям автоматической валидации образа жюри.

Для достижения главной цели соревнования — **Budget-Aware Token Estimation** — используется гибридная архитектура, сочетающая локальную детерминированную обработку и контролируемые обращения к LLM.

### Основные архитектурные решения

1. **Deterministic-First / Zero-Token Strategy**

   Вместо использования исключительно высокоуровневых абстракций фреймворка, которые могут скрывать дополнительные расходы токенов на внутренние вызовы, реализован собственный слой оркестрации на базе `asyncio`.

   Он позволяет применять детерминированные эвристики:
   - AST-мутации для задач категории `coding`;
   - regex-парсинг для задач категории `math`;
   - локальный анализ CSV-файлов для `data_analysis`.

   Если задача успешно решается локально, обращение к LLM не требуется — расход составляет **0 токенов**.

2. **Полный контроль над API**

   Для взаимодействия с языковой моделью используется `openai.AsyncOpenAI` с параметром `max_retries=0` и ограничениями `max_tokens` для каждого типа задач.

   Это позволяет избежать неконтролируемых повторных запросов и ограничить расход токенов при генерации.

3. **Безопасность и изоляция**

   Исполняемые скрипты запускаются через `subprocess` с предварительной санитизацией.

   Таймауты контролируются на уровне `asyncio.wait_for`, что позволяет предотвращать зависание всего агента из-за одной проблемной задачи.

Такой подход направлен на решение максимального количества задач при минимальном расходе токенов и позволяет сохранять значительный запас относительно общего бюджета.

## 🎯 Ключевые стратегии оптимизации

### 1. Оценка стоимости и детерминированное решение

Перед каждым обращением к LLM агент пытается решить задачу локально.

**Math**

- Анализ текстовых условий с помощью регулярных выражений.
- Использование шаблонов вроде `split equally`, `doubled`, `ships X per day`.
- Локальное вычисление результата без обращения к модели.
- Использование LLM только в качестве fallback, если детерминированный подход неприменим.

**Data Analysis**

- Проверка наличия исходного CSV-файла.
- Проверка соответствия структуры данных и требуемых колонок.
- Распознавание шаблонных аналитических запросов.
- Выполнение расчётов с использованием встроенного модуля `csv`, если структура задачи позволяет обойтись без LLM.

**Coding**

1. **Проверка существующего решения.** Запуск тестов до обращения к LLM. Если все тесты проходят, задача считается решённой с расходом 0 токенов.
2. **AST-мутации.** Поиск и исправление простых логических ошибок без использования LLM. Примеры: `sorted` → `reversed`, `<` → `>`.
3. **LLM fallback.** Если локальные методы не помогли, агент обращается к модели с требованием вернуть полный исходный код.
4. **Валидация результата.** Проверка синтаксической корректности через `ast.parse` и сохранения исходных сигнатур функций.

### 2. Детекция невыполнимых задач (Pre-flight Checks)

Для сокращения бесполезных обращений к LLM перед выполнением задачи проводятся быстрые локальные проверки.

Это особенно важно для задач, в которых необходимая информация или исходные данные отсутствуют.

**Search**

- Проверка наличия искомой сущности (имени, компании и т. д.) хотя бы в одном файле директории `kb/`.
- Если необходимые сведения не обнаружены, задача не передаётся на дорогостоящую обработку через LLM.

**Data Analysis**

- Проверка существования исходного файла.
- Проверка наличия колонок, упомянутых в инструкции.
- Отсечение задач, для выполнения которых отсутствуют необходимые данные.

**Coding**

- Проверка существования исходного файла.
- Проверка синтаксической валидности исходного кода.
- Предварительная оценка возможности исправления задачи.

### 3. Жёсткий контроль бюджета и времени

Для стабильной работы в условиях ограниченных вычислительных ресурсов реализованы следующие механизмы:

| Механизм | Назначение |
|---|---|
| `Safety Margin` | Использование 95% доступного бюджета для предотвращения превышения лимита |
| `TASK_TIMEOUT` | Ограничение времени выполнения одной задачи до 300 секунд |
| `FINISH_BEFORE_END` | Прекращение получения новых задач за 300 секунд до завершения общего времени |
| `max_retries=0` | Отключение автоматических повторных запросов к API |
| `max_tokens` | Ограничение генерации для каждого типа задач |

Общее ограничение времени выполнения — **1 час**.

Механизм Graceful Shutdown позволяет завершить уже запущенные вычисления и корректно остановить агента до истечения общего временного лимита.

## 📊 Сбор и анализ траекторий (Trajectories)

Для анализа поведения агента и последующей отладки реализовано логирование траекторий выполнения задач.

По умолчанию данные записываются в:

```text
/tmp/trajectories.jsonl
```

Путь можно изменить с помощью переменной окружения `TRACE_FILE`.

Каждая запись содержит информацию о выполненной задаче, использованном методе и расходе токенов.

Пример записи:

```json
{
  "ts": 1794386839.3,
  "task_id": "math_0000",
  "type": "math",
  "reward": 5,
  "method": "deterministic",
  "ok": true,
  "tokens": 0.0,
  "note": ""
}
```

### Описание полей

| Поле | Описание |
|---|---|
| `ts` | Временная метка выполнения |
| `task_id` | Уникальный идентификатор задачи |
| `type` | Категория задачи (`math`, `coding`, `search` и т. д.) |
| `reward` | Полученная награда |
| `method` | Использованный способ решения |
| `ok` | Статус успешного выполнения |
| `tokens` | Количество использованных токенов |
| `note` | Дополнительная информация о выполнении |

Поле `method` позволяет определить, каким способом была решена задача:

- `deterministic` — детерминированное локальное решение;
- `mutation` — решение с помощью AST-мутаций;
- `llm` — решение с использованием языковой модели;
- `already-passing` — исходное решение уже проходило тесты.

Собранные траектории позволяют анализировать эффективность различных стратегий, сопоставлять успешность решений с расходом токенов и калибровать оценку стоимости выполнения задач.

## 🚀 Сборка и запуск

### Локальная разработка

**Требования:**

- Python 3.11 или новее;
- API-ключ совместимого LLM-провайдера;
- установленный `pip`.

#### 1. Подготовка переменных окружения

Создайте файл `.env` в корневой директории проекта.

Файл `.env` добавлен в `.gitignore` и не должен попадать в репозиторий.

Пример содержимого:

```bash
export LLM_API_KEY="sk-ВАШ_РЕАЛЬНЫЙ_КЛЮЧ"
export LLM_BASE_URL="https://api.neuraldeep.ru/v1"
export TASKS="./local_tasks"
export BUDGET=100000
```

#### 2. Активация окружения и установка зависимостей

```bash
source .env
pip install -r requirements.txt
```

#### 3. Запуск агента

```bash
python3 run_agent.py --tasks-dir ./local_tasks
```

---

### Docker: эмуляция среды жюри

Для проверки работы в условиях, приближенных к регламенту соревнования, предусмотрена сборка Docker-образа.

Ожидаемые характеристики образа:
- время сборки — менее 1 минуты;
- размер — около 300 МБ;
- ограничение размера по регламенту — 4 ГБ.

#### 1. Сборка образа

```bash
docker build -t gradient-ai-harness:latest .
```

#### 2. Запуск в изолированной среде

```bash
docker run --rm \
  -e LLM_API_KEY \
  -e LLM_BASE_URL \
  -e TASKS="/data/tasks" \
  -e BUDGET \
  -v "$(pwd)/local_tasks:/data/tasks:rw" \
  --cpus 8 \
  --memory 16g \
  --read-only \
  --tmpfs /tmp:rw,size=2g \
  gradient-ai-harness:latest
```

**Примечание:** флаг `-e VAR` без явного значения автоматически передаёт переменную окружения из текущей оболочки. Для этого предварительно выполните `source .env`.

## 🏆 Основная идея проекта

**GradientAI Harness** строится вокруг простого принципа:

> Не использовать токены там, где задачу можно решить детерминированно.

Вместо того чтобы отправлять каждую задачу в языковую модель, агент сначала анализирует её структуру, проверяет доступные данные и применяет локальные алгоритмы.

LLM используется только в тех случаях, когда детерминированные методы оказываются недостаточными.

Это позволяет сосредоточить ограниченный токенный бюджет на действительно сложных задачах и повысить количество потенциально успешно решённых заданий.
