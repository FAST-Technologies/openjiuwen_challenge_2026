# Budget-aware харнесс на openJiuwen (НГУ, 07–20.11.2026)

Харнесс получает каталог задач и бюджет токенов (`BUDGET`, по умолчанию 100 000) и решает как можно больше
задач (по сумме `reward`), тратя как можно меньше токенов. Идея: **сначала дёшево выяснить, что именно нужно
каждой задаче, и только потом тратить токены** — большинство задач решается кодом, LLM нужна как запасной путь.

## Сборка и запуск

```bash
docker build -t hack:latest .
docker run --rm --network hack-net -e LLM_BASE_URL -e LLM_API_KEY \
  -v "$TASKS:/data/tasks:rw" --read-only --tmpfs /tmp:rw,size=2g -e HOME=/tmp \
  --cap-drop ALL --security-opt no-new-privileges --workdir /app --entrypoint python \
  hack:latest /app/run_agent.py --tasks-dir /data/tasks
```

Локально (после `pip install -r requirements.txt`, Python 3.11–3.13):

```bash
export LLM_API_KEY=...            # ключ не хранится в репозитории и не попадает в образ
export LLM_BASE_URL=https://api.neuraldeep.ru/v1
export BUDGET=100000
python run_agent.py --tasks-dir ./local_tasks
```

| Переменная / параметр | Назначение | По умолчанию |
|---|---|---|
| `--tasks-dir` / `TASKS` | каталог с задачами | `/data/tasks` |
| `LLM_BASE_URL`, `LLM_API_KEY` | прокси организаторов и ключ | — (ключ обязателен) |
| `BUDGET` | бюджет в выходных токенах (10 входных = 1 выходной) | `100000` |
| `OUT` | необязательно: файл или каталог для сводки `results.jsonl` | не задан |
| `CONCURRENCY` | параллельных задач / запросов к LLM | `3` |
| `TIME_LIMIT_SEC` | жёсткое время работы | `3600` |
| `TRACE_FILE` | куда писать траектории (jsonl) | `/tmp/trajectories.jsonl` |
| `OJ_LOG_LEVEL` | уровень логов openJiuwen | `WARNING` |

Ответ задачи — файл `answer.txt` **рядом с `task.json`**. Для невыполнимых задач файл не создаётся
(так просили организаторы). Файл пишется сразу после решения каждой задачи.

## Как устроен харнесс

```
run_agent.py ── TaskRouter ── worker.estimate()  (0 токенов)  →  plan: free | llm | unsolvable, оценка расхода
      │
      ├─ очередь по ROI = reward / max(оценка, 10); невыполнимые не запускаются
      └─ 3 consumer'а:  worker.solve(task)
             1. детерминированный путь (код, 0 токенов)
             2. один дешёвый вызов LLM (qwen3.6-35b-a3b-noreason; coding: + qwen3.6-35b-a3b)
             3. эскалация: ReAct-агент openJiuwen с инструментами в каталоге задачи (жёсткий потолок токенов)
```

### Использование openJiuwen (версия `0.1.19`, зафиксирована в `requirements.txt`)

- `llm_client.py` — все обращения к моделям идут через `openjiuwen.core.foundation.llm.Model`
  (`ModelClientConfig` + `ModelRequestConfig`); расход берётся из `usage_metadata` ответа.
- `escalation.py` — `ReActAgent` (`ReActAgentConfig`, `AgentCard`) с инструментами `LocalFunction`/`ToolCard`:
  `list_dir`, `read_file`, `write_file`, `run_python`, `run_file`. Модель агента — `BudgetedModel`
  (наследник `Model`), который записывает расход каждого вызова в общий `BudgetTracker` и прерывает агента
  при превышении потолка на задачу.
- `oj_setup.py` — отключает файловые логи openJiuwen (по умолчанию он пишет в `./logs/`, а `/app` в контейнере read-only).

## Оценка расхода токенов (до запуска, без LLM)

Каждый воркер реализует `estimate(task)` и возвращает класс задачи и ожидаемый расход (в «выходных» токенах;
деление на 35 = 3,5 символа на токен ÷ 10 за вес входа):

| Тип | `free` (0 токенов) | `llm` — оценка | `unsolvable` |
|---|---|---|---|
| math | текст разобран шаблонным парсером | `70 + len(текст)/35` | — |
| data_analysis | вопрос разобран, CSV прочитан | `120 + len(текст)/35 + len(заголовок)/35` | нет CSV, пустой CSV, в CSV нет колонок из условия |
| search | цепочка по `kb/` пройдена кодом | `15 + (len(релевантных файлов)+len(вопрос)+200)/35` | сущности из вопроса нет в `kb/`, нет каталога `kb/` |
| coding | — (всегда `llm`, как верхняя оценка) | `150 + (len(lib)+len(test))/35 + len(lib)/3.5·1.3` | нет `mylib.py` или тестов |

Порядок выполнения — по убыванию `reward / max(оценка, 10)`. Оценки консервативные (верхние): coding оценивается
как LLM-путь, хотя часть багов чинится перебором мутаций бесплатно. Константы получены из размеров входа и
замеров на примерах, **не откалиброваны на большой выборке** (скрытого набора нет, трасс организаторы не дают);
калибровка по своим запускам — поле `est` против `tokens` в траекториях (см. ниже).

### Защита бюджета

- Расход считается по `usage` ответа: `completion + prompt/10`, токены рассуждений входят в выходные.
  Если провайдер не вернул `usage` — оценка по длине текста (3,5 символа на токен).
- Перед стартом задачи проверяется `потрачено + оценка ≤ 0,95·BUDGET`; запас 5% — прокси обрывает ответы резко.
- У каждого вызова задан `max_tokens` (math/data ≤ 600, search = 40, coding 1500 → 4000 для reasoning-модели, агент 900).
- SDK-ретраи отключены (`max_retries=0`), повторы делает `LLMClient` сам, каждый запрос учитывается.
- Эскалация: потолок `min(6000, 6% бюджета)` на задачу, ≤ 6 шагов, таймаут 240 с, и не стартует, если осталось
  меньше 25% бюджета. Ошибки агента не роняют прогон.
- Время: 3 задачи параллельно, ≤ 420 с на задачу, новые задачи не запускаются за 300 с до часа.

## Как распознаются невыполнимые задачи

Никаких токенов на «попытки» невыполнимых задач не тратится — признаки проверяются кодом до запуска:

1. **data_analysis**: нет файла CSV, он пуст, или колонки, названные в условии, отсутствуют в заголовке.
2. **search**: в вопросе есть имя («Имя Фамилия»), которого нет ни в одном файле `kb/`. Если сущность есть, но
   нужного поля в цепочке нет, это не объявляется невыполнимым сразу (мог не сработать парсер формулировки):
   вопрос уходит в LLM с релевантными файлами, а ответ `NOT FOUND` означает «ответа нет, файл не создаётся».
3. **coding**: нет `mylib.py`/тестов. Если после всех попыток (мутации → LLM → агент) тесты не проходят, исходник
   восстанавливается, `answer.txt` не создаётся.
4. **Неизвестный `task_type`** пропускается.

Не распознаётся заранее: невыполнимая math-задача (с недостающими данными) — парсер вернёт «не разобрано»,
LLM-программа либо не выполнится, либо ответ не нормализуется в целое: файл не создаётся, но токены уйдут.

## Что делает каждый воркер

- **math** — парсер шаблонных предложений («starts with N», «split equally into K … rounded down», «doubled»,
  «ships X per day for D days», «receives N deliveries of X each»). Не разобрано → LLM пишет короткую программу,
  она исполняется **без shell** (`python -c`, список аргументов) → при неудаче эскалация.
- **data_analysis** — вопросы вида «units of product 'X' in months A through B» считаются `csv`-кодом. Иначе LLM
  пишет скрипт (исполняется без записи файлов), затем эскалация. Ответ нормализуется по `check` (`exact_int`).
- **search** — `kb/*.md` разбираются в граф (`# Заголовок`, строки `Ключ: значение`); вопрос решается обходом
  цепочки (`Employer → Headquarters`, `Mentor → Born`, …). Иначе в LLM уходят только релевантные файлы (а не вся база).
- **coding** — (1) перебор одиночных мутаций AST (`<`↔`>`, `+=`↔`-=`, `sorted`↔`reversed`, `== 1`↔`== 0`, …) с
  выбором по числу упавших тестов — 0 токенов; (2) LLM: `noreason`, затем reasoning-модель, в промпт идут исходник,
  тесты и вывод; ответ проверяется `ast.parse`, сохранностью всех функций, снимается общий отступ; (3) агент.
  Итог всегда проверяется собственным запуском тестов, а не словами агента.

## Безопасность

Исполняется только код из условия задачи и ответов модели: `python` в каталоге задачи, без shell, таймаут,
без сети (контейнер её не имеет). Инструменты агента не выходят за каталог задачи, не меняют `test_*` и `answer.txt`.
Ключ читается только из окружения; в образ копируются только файлы харнесса (`.dockerignore`).

## Траектории

Каждая задача пишет в `TRACE_FILE` одну строку JSON: `task_id`, `type`, `reward`, `plan` (класс по оценке),
`est` (оценка до запуска), `method` (`deterministic` | `mutation` | `llm` | `agent` | `precheck` | `llm+agent`),
`ok`, `tokens` (фактический расход задачи), `note`. Пример (прогон **с поддельным LLM-сервером**, не реальной модели —
показывает формат и пути решения):

```json
{"task_id": "math_0000", "type": "math", "reward": 5.0, "method": "deterministic", "ok": true, "tokens": 0.0, "est": 0.0, "plan": "free"}
{"task_id": "coding_0003", "type": "coding", "reward": 2.0, "method": "mutation", "ok": true, "tokens": 0.0, "est": 327.1, "plan": "llm"}
{"task_id": "math_jars", "type": "math", "reward": 1.0, "method": "agent", "ok": true, "tokens": 126.8, "est": 77.5, "plan": "llm"}
```

## Ограничения и открытые вопросы

- Парсеры настроены на формулировки из 8 примеров; другие формулировки уходят в LLM-путь (дороже, но работают).
- Мутации подгоняют код под **видимые** тесты; если проверка идёт по другим скрытым тестам, результат может отличаться.
- Тесты проверены на поддельном LLM-сервере; поведение настоящих `qwen3.6-35b-a3b*` (качество ответов, реальный
  расход, тримминг рассуждений) измеряется только реальными прогонами.
- Харнесс использует две модели одного семейства (`qwen3.6-35b-a3b` и `qwen3.6-35b-a3b-noreason`).
- Образ в среде разработки собрать не удалось (нет Docker-демона): проверена установка `requirements.txt` в чистое
  окружение, но не сама сборка; тег базового образа нужно заменить на точный (см. комментарий в `Dockerfile`).
